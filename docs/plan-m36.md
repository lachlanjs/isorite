# M36: the isorite harness, and a deeper MCP route for the user's own

Why: isorite's agent integration has two jobs that want different tools. Building the project is done best in the user's own harness, with their skills, MCP servers and subagents. Building and tending the knowledge base wants an agent that is tied to it: a highlight in a note goes straight into the prompt, the person sees how the agent's words and steps relate to the notes, and what the agent holds in context can be shaped. M35 showed the second can be built on pi and what it costs. This milestone turns the prototype into something a person can use daily, and makes the first job's route (MCP) as good as it can be without owning the user's harness.

## Decided

- Two modes, used together. **Your harness over MCP**: the user's own agent reads and writes the notes through isorite's MCP server, and the Atlas and the pane show what it did. This is one-way and the user keeps all their agentic tooling. **The isorite harness**: an agent that runs inside isorite, for tending the knowledge base, with two-way integration (highlights, chips, context control). The recommended flow runs both at once.
- The isorite harness is native: pi (`pi-ai`, `pi-agent-core`) behind the `PaneSessions` seam, with isorite's own session store, approvals and event model. It is the same code behind a web pane and, later, a terminal interface; both are clients of the same server session.
- Its tools: the base's own note tools always. Project files, read-only (read, grep, find, ls), on by default. Project writes: opt-in. Shell: opt-in and off by default, because the isorite agent is for the knowledge base, not the codebase. Where the shell is on, the settings say plainly that nothing confines it (M35, step 5).
- Credentials: API keys, and OpenRouter's sign-in (it mints a key). No Claude subscription login: Anthropic's terms refuse it for a product like this (M35, step 7). A ChatGPT sign-in is added only after OpenAI's terms are read at the source.
- The existing ACP route (the pane driving the user's own agent, `isorite acp`) is kept, and gets three small additions that ride on the native work and nothing else: chips sent as embedded resources (3b), steers sent through `_session/steering` (6b), and the subagent capability declared so child sessions can be told apart (in step 4). Step 2 found the Claude and Codex adapters support all three. It is not removed in this milestone. It is the only way a Claude subscription pays for work in the pane (terms still open, step 2), so its removal is a separate decision to make once the native harness covers daily use.
- Build on a new branch, `m36-isorite-harness`, off `m35-pi-harness`. The pane seam, the chips and the pi host come with it. Nothing is merged to `main` or pushed in this milestone without the owner's say-so, and `m28-chat` is left alone.
- The first step is verification of the ACP side (adapters and terms), because it decides whether freezing ACP is safe. The swarm display (several agents at once on the Atlas) is a feasibility test only.

## The shape

- One session model, `TerminalView`, read by every client. It gains what pi has and ACP lacks: a message queue (steer and follow-up), thinking, and a compaction marker. The ACP path never fills them.
- `PaneSessions` grows from one session to several for the native agent: list, open, resume, fork, forget.
- A session store of isorite's own holds the model's context between runs (the messages pi needs), apart from the pane's record of turns, which exists already. It lives in isorite's data folder for the base, not in the notes' repository.
- The tray becomes the agent's context for the native harness. Each chip is tagged when it is sent; removing a chip withdraws that block from the next request. This is the thing only an owned loop can do, and it is the reason for this harness to exist.
- Tools come in three tiers, set per base in settings: notes (always), project read (on), project write and shell (off). A guard in `beforeToolCall` enforces the tiers and fails closed, as in M35.
- A terminal interface attaches to the same `/api/terminal` routes and event stream as the web pane. It is a client, not a second agent.
- For the user's own harness: the same MCP server, plus a copy-and-paste handoff that tells the agent which notes to read, and the work to tell agents apart on the Atlas if their clients allow it.

## Found so far (what is already there)

- The pane's ACP side starts an agent chosen from the ACP registry (for Claude, `npx -y @agentclientprotocol/claude-agent-acp`; for Codex `@agentclientprotocol/codex-acp`; OpenCode, omp and Hermes by their own `acp` commands) with the server's environment (`agents.ts`, `detect.ts`).
- In pane mode the wrapper introduces itself as an ACP client with file and terminal access switched off (`fs: false`, `terminal: false`, `acp-wrap.ts`), so the agent uses its own tools, shell included. isorite can only refuse a call by answering a permission request.
- The wrapper adds isorite's MCP server to each new or resumed session when the agent accepts HTTP MCP servers.
- The pane already carries chips from the tray (M35 step 4) and a `PaneSessions` seam (step 2). The pi host (step 3 and after) serves one session at a time, refuses a prompt while busy, drops thinking, and does not keep the model's context between runs (M35 step 6).
- The MCP look-up path takes an agent and session name (`agentLook`), so a call is already shown as a step on the Atlas. Whether real MCP clients supply a name that tells their subagents apart is not known.

### Step 11: several sessions

- **Shape.** The host still has one session live at a time (its fields are the session shown); the others are kept on disk, one file each, and listed from there. Switching writes nothing new (the shown session was written after its last turn) and loads the other into the host. This is the smallest change that gives the pane two sessions with their own turns, messages, given-set and cost, and it keeps one running loop. It also means a session cannot be left while the agent is working in it: switching, forking, starting a new one or forgetting the shown one is refused with "stop it first". Several sessions *working* at once is the next step if it is wanted, and is not built.
- **What the pane can do** (the drawer that was already there for ACP agents' sessions): list the sessions kept, newest first, with the one shown marked live; show one (`follow`), start a new one (`fresh`; the old one stays kept), forget one (`forget`; the shown one too, leaving the pane empty for a new one), and **fork** one. After a restart the last changed session is shown and the rest are listed.
- **Fork.** A new session that begins with a copy of the original's turns and messages, titled "<title> (fork)", with its cost starting at nothing; the original is untouched. New route `POST /api/acp/fork` (409 for hosts that cannot) and a "fork" action in the drawer.
- **Store.** `PiStore` gains `list` (unreadable files are named in the pane and left, not dropped), `load` and `remove`; ids must look like ids, so a path cannot be asked for.
- **Checked.** `pi-sessions.test.ts` (5): two sessions with their own turns and the model carrying on from its own messages only; costs kept per session from seeded records and a fork starting at 0; a missing id or a path refused; a fork leaving its original unchanged; forgetting one, including the shown one, and a restart finding the rest. `sessions.spec.ts` on desktop and phone drives the drawer: list, switch, fork, forget. It is skipped unless the server is started with `ISORITE_PI` (the normal suite's server has no native agent), so I ran it by hand with `ISORITE_PI=openrouter/anthropic/claude-haiku-5.5` (no key is used).
- **Not tested / limits.** The costs are checked from seeded records because pi's scripted provider always reports zero cost. Listing reads every kept file; with hundreds of long sessions that will want an index. The `sessions.spec.ts` is not part of the normal run.

### Step 10: context from the tray

- **Tagging.** For the native agent, each chip given with a question is its own block in the message, wrapped `[context <key> @<turn>] ... [/context]`, so the block can be found again in the saved messages. (Before, the blocks were joined into the question's text.)
- **Withdrawing.** Taking a chip out of the tray (in the pane, the context list or the Atlas lens) tells the server (`POST /api/terminal/withdraw`), and the host marks every block given with that chip as withdrawn. From then on, every request to the model, and the input of a summary, carries one line in its place: the person took that context out, do not rely on it. The turns it came in stay in the pane with the chip struck through and a title saying why. Put in again, the chip is given afresh with the next question; the old block stays withdrawn. The withdrawn set is kept with the session.
- **A reload is not a withdrawal.** The tray lives in the page and is empty after a reload, so withdrawing is an explicit request made when a chip is taken out, not inferred from the tray being short; a restart or a reload withdraws nothing.
- **ACP agents.** The request is made but nothing is withdrawn: an ACP agent keeps its own history, which isorite cannot edit. The pane does not say it did.
- **Dragging.** Notes are carried into the box from the note list and the Atlas by the existing press-and-drag gesture, and passages by "add to Iso's message" on a selection; there is no browser drag-and-drop of text into the box, and none was added.
- **Checked.** `pi-withdraw.test.ts` (3): a withdrawn passage is gone from the next request while the other chip stays and the turn keeps it, marked; a chip put in again is given once, afresh, with the old block still withdrawn; the withdrawal survives a restart, and a restart with an empty tray withdraws nothing. `withdraw.spec.ts` on desktop and phone: removing a given chip sends the request and an ACP agent is not disturbed.
- **Not tested.** That a summary leaves a withdrawn block out: the summary's input goes through the same function as every request, but no test inspects it.

### Step 9: tool tiers

- **Tiers.** Project files: none, read, or read and write; and a shell, on or off. The base's own tools are always on. The default is read, no write, no shell (it was none before: the plan says read is on by default, because reading the project is how the agent answers about the code a note describes).
- **Where set.** Iso's settings, under the model: radios for the files, a checkbox for the shell, and under each choice a line on what it promises and what it does not. Kept in the same owner-only file as the keys (`reach`), applied at the next question (the tools are made when a question starts), held across restarts. `ISORITE_PI_FILES` and `ISORITE_PI_SHELL` still work, win while set, and the settings say so and disable their controls.
- **What the lines say.** Read: it can see everything there that you can, including files with secrets, and cannot change anything. Write: it changes your files directly, never in `.git`; keep the project in version control. Shell: not confined; it runs as you and can read or change any file, use the network and reach outside the project, the path checks do not apply; confine it with a container or disposable VM or a separate user account that has only the project, or leave it off.
- **Checked.** `pi-tiers.test.ts` (3): a default session reads and every attempt to write, edit or run a command fails with the file unchanged; turning write, then shell, on in the settings applies to the next question, survives a restart, and turns off; the environment wins and a bad value is named. `pi-reach.test.ts` (unchanged) still covers the path guard. `models.spec.ts` (second test) on desktop and phone: defaults, the shell's warning in words, a change kept after a reload.
- **Not done.** Asking before write or shell by default (`ISORITE_PI_ASK` exists; the settings do not expose it); confining the shell (nothing in isorite does).

### Step 8: models and keys

- **Where things are kept.** `pi/credentials.ts`: one file, `$XDG_DATA_HOME/isorite/credentials.json` (mode 0600, folder 0700, written whole and renamed), holding the keys by provider and the model chosen. It is in isorite's data folder, apart from the notes and the repository. An unreadable or foreign file is reported by name and left alone.
- **Which key is used.** The saved key, else the provider's own variable (`OPENROUTER_API_KEY`, ...). The host asks for it at each request (pi's `getApiKey`), so a key entered or removed in the settings is the next turn's. The pages are told only where a key comes from (saved, environment, none), never what it is; a rejected key is not repeated in the error.
- **Which model.** `ISORITE_PI` wins while it is set; otherwise the model chosen in the settings. A host already running is moved to the new model for its next request (`PiHost.use`); where no host is running (the pane is still an ACP agent's) the choice takes effect at the next start, and the settings say so. Making the pane switch from ACP to the native agent without a restart is not built: it needs the pane's host to be replaceable while the server runs.
- **Providers offered.** Eleven that are used with an API key (OpenRouter, Anthropic, OpenAI, Gemini, Mistral, Groq, xAI, DeepSeek, Together, Fireworks, Cerebras). Pi's subscription sign-ins (ChatGPT, Copilot) and "sign in with OpenRouter" are not offered: the first by the earlier decision not to rely on terms that are not ours, the second because a key pasted from OpenRouter's page does the same with nothing to build or secure.
- **Routes.** `GET /api/pi`, `POST /api/pi/key`, `POST /api/pi/key/remove`, `POST /api/pi/choose`; from this machine only (a request by another name is refused).
- **Settings.** A section in Iso's settings, under AGENTS.md: provider, "a key is saved" line, a password box that is emptied after saving, remove, model name, and a note on where keys live.
- **Checked.** `pi-keys.test.ts` (5): owner-only modes, keep and remove, environment fallback and its label, refusal of bad keys and providers, an unreadable file named and untouched, the key carried by the next request and gone after removal, the routes never returning or logging a key (console captured), and absent from the base and, once removed, from the data folder. `models.spec.ts` on desktop and phone. A real run with the key only in the credential store (no environment variable): `claude-haiku-5.5` through OpenRouter answered "key works", cost $0.00035.
- **Not done.** Listing a provider's models (the model is typed); a way to test a key from the settings; keeping keys in the system keychain instead of a file (the file is what pi's own tools do too).

### Step 7: thinking and compaction

- Two new kinds of item in a turn: `thinking` (the model's reasoning, folded in the pane under "thinking") and `compaction` (running, done or failed; the size before and after in tokens, and the summary). The pi host folds `thinking_delta` into a thinking item ahead of the answer it belongs to, and replaces it with the whole reasoning when the message ends (a redacted, empty one is dropped). ACP agents' `agent_thought_chunk` now fills the same item, so thinking shows for them too.
- Compaction (pi host): before a prompt, if what the model would be sent nears its window (pi's `shouldCompact`, with pi's default reserve of 16,384 tokens and 20,000 kept recent, both overridable), the earlier part of the conversation is summarised by pi's `generateSummary` through the same model and key, and replaced by one message that begins "[The earlier part of this conversation, summarised to make room]". The recent part is kept as it was, cut at a message of the person's so a tool call and its result stay together; leading system messages stay; a later compaction merges into the earlier summary. The turn shows it as an item, and the stop button stops it. If the summary cannot be made, the turn says so and the conversation goes on as it was.
- The size of the context after a compaction is estimated (characters over four), because the recent answers' own counts describe the context as it was; they are zeroed so they are not trusted until the model's next answer gives a count. The system prompt is no longer saved with a session's messages (pi puts it first in its message list); the agent has its own at each start.
- Tests: `pi-thinking.test.ts` (3: thinking ahead of a tool and an answer, kept whole; a long conversation summarised before a prompt, with the first question gone and the recent one kept, then carrying on with the summary in front; a failed summary leaving the conversation as it was), `thinking.spec.ts` (the folded item in the pane, desktop and phone, via an ACP agent), `pi-loss.test.ts` updated (thinking is now in the view). Server suite 134 of 135 (the known `model.test.ts`), type checks clean, the affected browser specs pass.
- With a real model (`claude-haiku-5.5` through OpenRouter, an artificially small window of 10,000 tokens so that compaction fires): six turns each carrying about 1,400 tokens of padding, then "what is my dog called and when does my train leave?" with the dog and the train given in the first two turns. Compaction fired from the fourth turn (8,122 to 4,969 tokens; later 8,465 to 5,007 and 8,523 to 5,043), and the answer was "Your dog is called Biscuit, and your train leaves at 07:42." The summary kept both facts through three compactions. It fires on nearly every turn because the window was made small; with a real window it would be rare. The checks cost under a cent each.
- What the real model also showed: two attempts with a smaller window (3,600 and 6,000 tokens) gave answers cut to one letter, `stop: length`, and in one a summary "hit the token cap". Pi limits a reply to what is left of the window and a summary to a fraction of the reserve, so a window smaller than the context plus the reply (never so with a real model's window) starves both. Not a fault of the host, but it means a `compaction` override should keep the reserve well above the summary's size.
- Not done: asking for a compaction by hand (a `/compact` command); showing what the summary dropped; the thinking of models that stream it only at the end is shown whole at the end.

### Steps 6 and 6b: saying something while the agent works

- A new kind of item in a turn, `message` (`mode` steer or followUp; `state` queued, landed, sent or dropped), and `TerminalView.steer` for whether the session shown can be steered. `PaneSessions` gains an optional `steer(text)`; the server gains `POST /api/terminal/steer`, which refuses with the reason where the host cannot.
- The pi agent: a prompt sent while it works is no longer refused. It becomes a follow-up (pi runs it when the agent would otherwise stop); `steer` puts it in after the step running now. Each shows at once as a queued item, and when the model takes it up pi emits it as a user message, which the host matches to the item and moves to where it came in, as `landed`. A stop clears the queues and shows what had not been taken up as `dropped`.
- ACP (6b): where an agent advertises `_meta.steering.supported` at initialize, the follower sends `_session/steering` into the running turn and shows the item as `sent` (the agents do not say when they take it up). Where it does not, the request is not sent and the pane says "cannot be steered while it works: stop it and ask again". A prompt sent while an ACP agent works already waited in the wrapper until the agent was free; it still does, and the pane does not show it as queued.
- The pane: Enter while the agent works adds the message for when it stops; with an agent that can be steered, a "Steer now" link (or Ctrl+Enter) puts it in after the step running now. Each message shows in the turn as "steer" or "next", faint and "waiting" until taken up.
- Tests: `pi-queue.test.ts` (3: a steer reaches the model's next request and stands after the tool it waited for; a follow-up is taken up after the first answer; a steer when idle is refused and a stop drops what waited), `acp-steer.test.ts` (2: an agent that takes steering is sent it and the turn shows it; one that does not is not sent the request and the pane says why), `steer.spec.ts` (the pane, on desktop and phone), and the earlier pane, ACP, chips and handoff specs still pass. Server suite 131 of 132 (the known `model.test.ts`), type checks clean. The full browser suite was not re-run.
- Not done: a way to take back a queued message, and queued messages for an ACP follow-up. Thinking and compaction are step 7.

### Step 5: the model's context kept between runs

- `packages/server/src/pi/store.ts`: `FileStore` keeps one JSON file per pi session holding the pane's turns, the model's messages (pi's, as they are), the cost, the size used and the keys of what was given. It is written to a temporary file and renamed, so a file is never half written, with owner-only permissions. The folder is isorite's data folder per base, `$XDG_DATA_HOME/isorite/pi/<12 hex of the notes path>/`, apart from the notes and the repository.
- `PiHost` takes a `store`; after each turn it writes the session (not waited for), and `resume()`, called once at start by `piHostFor`, takes up the session last changed: its turns appear in the pane and the agent is built with the saved messages, so the model carries on. A turn that was running when the server went down comes back `stopped`.
- A file that cannot be read (not JSON, or not a session this version wrote) is reported in the pane's `problem` with its full path, left where it is, and the agent starts fresh; the new session is kept beside it. Nothing is deleted.
- Tests: `pi-store.test.ts` (4): a restart resumes the session and the model's next request carries the earlier question and answer; a running turn returns stopped; an unreadable file is reported, kept, and a new session is written beside it; the folder is under the data folder and differs by base. The pi, reach and loss suites and the full server suite still pass (apart from `model.test.ts`).
- With a real model (`claude-haiku-5.5` through OpenRouter, two separate processes over one folder): told "my project is called Heron and my favourite number is 17", then after a restart asked without being allowed to look it up, it answered "Your project is called Heron, and your favourite number is 17."
- Limits: one session is resumed (the last changed); keeping and choosing among several is step 11. A write is not waited for, so a hard exit within a moment of a turn ending can lose that turn (a first attempt at the real-model check did exactly that, because the script exited at once). A turn is written only when it ends, so a crash mid-turn loses that turn. Pi's message format is the file's format, so a pi upgrade that changes it can make old sessions unreadable, which will be reported, not hidden. The files hold what was said to the model, in the clear.

### Step 4: telling agents apart (scripted and read from code; no real client run yet)

Over ACP:
- In pane mode isorite now declares `clientCapabilities.subagents` itself (`acp-wrap.ts`), so the Claude and Codex adapters (step 2) report each subagent as a session of its own instead of a tool call of the parent's. Behind a front end the front end's capabilities are passed through, so a front end that declares it gets the same.
- The follower (`acp.ts`) reads `subagent_update`: it shows the subagent as a step in the parent's turn (running, then done or failed from its state), and keeps a hidden session for it. What that session reads or changes in the base is told under its own name, `<agent>-<first three words of its title>-<n>` (`scripted-scout-one-1`), so the Atlas sees a separate agent. The drawer does not list it. Without this, declaring the capability would have dropped a subagent's reads, since updates for a session the follower does not know are ignored.
- Tests: `acp-subagents.test.ts` (three): a front end that declares it gets two steps and two named agents; one that does not gets the work under the parent's name, as before; and in pane mode isorite declares it itself. The scripted agent gained `delegate <path> <title>`.
- Not seen: the real adapters' child sessions. The shapes come from the adapter's README and source (`subagent_update` with `title`, `description`, `state.state` of `running`, `requires_action` or `idle`), not from a run. A child's own messages and its permission requests are not folded into the pane, and the pane does not yet say which subagent asked.

Over MCP:
- The endpoint keeps no session: a caller is `?agent=` on the address, else the client name a request carries in `_meta`, else `"mcp"` (`mcp-identity.test.ts`). A harness and its subagents given one address are therefore one agent, and a client that sends `clientInfo` only in `initialize` is `"mcp"` on its later calls, since the endpoint does not remember it.
- So over MCP alone a swarm is told apart only if each caller has an address of its own or names itself on every request. Claude Code's subagents do neither (the real-client run below).

A real client, run 2026-11-06: Claude Code 2.1.318 (signed in on this machine, model haiku, one short run, tools limited to the Agent tool and isorite's `search_notes`) was asked to start two subagents, each to make one `search_notes` call, against a local isorite server through a logging proxy. What it sent:
- Every request, including `tools/call`, carries `_meta` with `io.modelcontextprotocol/clientInfo` (name `claude-code`, title `Claude Code`, version 2.1.318), the protocol version and the client's capabilities; a `tools/call` also carries `claudecode/toolUseId` and a `progressToken`. The user agent is `claude-code/2.1.318 (sdk-cli)`. No session header; it opened with `server/discover`, then `resources/list` and `tools/list`.
- Both calls (`euler`, `leapfrog`) reached the base as one agent, `claude-code`, in one session, `http`. So over MCP Claude Code's subagents are not told apart: they share the client name, and nothing in the request names the subagent. I did not capture the transcript, so that the two calls were made by subagents and not by the main agent rests on the instructions given and the model's reply ("done"), not on proof.
- `claudecode/toolUseId` is a per-call handle. In an ACP session the adapter reports the same tool call to isorite, and the ids probably match, which would let isorite give an MCP call to the subagent session whose tool call it is. That is a guess to test, not a finding; it would only help for a session isorite hosts.

Conclusion for step 4: over MCP alone a swarm shows as one agent (as Claude Code is used in its own terminal, which is most people); over ACP, with the capability declared, each subagent can be its own agent on the Atlas, once the real adapters are seen to send what their source says. The swarm display stays a later step, built on the ACP route.

### Step 3b: chips as embedded resources for ACP agents

- The follower records whether an agent declared `promptCapabilities.embeddedContext` at initialize (`Link.embedded`). When the pane gives something and the agent did, each passage goes as a resource block after the given text: `{type: "resource", resource: {uri: "isorite://<base>/<note id>", mimeType: "text/markdown", text: <the passage>}}`, the same address the MCP server lists its notes under. The text then says the passages are attached, names the note each is from, and says to read the note for the current text. Notes and folders stay as text that points to `read_note` and `search_notes`: a note's whole body is not embedded, because the agent can read it through the tools and an embedded copy would go stale.
- An agent that did not declare it gets what it got before: the passage quoted in the text. `PaneSessions.give` takes the second renderer as an optional third argument; the pi host ignores it.
- The given block is still recognised by its first text block, so the pane's turn shows what was asked and what went with it as before.
- Tests: `acp-embedded.test.ts` runs the scripted agent twice, declaring and not declaring the capability; the first receives three blocks with the resource at the base's address and the second two with no resource. `acp.test.ts`, `pane-sessions.test.ts`, `pi-host.test.ts` and the ACP and chips browser specs still pass.
- Not tested: a real Claude or Codex adapter, which declares the capability in source (step 2) but has not been run here. What the real agent does with a resource block is for a run with the agents signed in.

### Step 3: the paste handoff

- `app/src/lib/handoff.ts`: `handoffText(parts, question)` writes the block: a line telling the agent to read what is named with isorite's tools (`read_note`, `outline_note`, `search_notes`, `brief_base`) and not from the message alone, then the notes and folders by title and id, then each passage quoted with its note's title and id, then the question typed in the box.
- The Iso pane now shows the tray's chips when no agent is attached (they were hidden then), with a "Copy for your agent" button under them. It copies the block, with whatever is typed in the box as the question.
- Tests: `handoff.test.ts` (3, the text for nothing, for each kind, for a passage alone) and `handoff.spec.ts` (a passage chosen in a note, copied with no agent attached, read back from the clipboard; Chromium only, on all four projects), with `composer-chips.spec.ts` still passing.
- A passage is quoted as it was when chosen and the block says to read the note for the current text, so an edit made since does not leave the agent holding a stale quote without being told. The ids in the block are the ones `read_note` takes (the pi tests read notes by the same ids).
- Not done: a test with a real or scripted MCP client reading from the pasted text. The plan's check asked for one; the text and the tool ids are verified separately, and what a model does with the block is only known by trying it with a real agent. That is one for the owner to do with their own harness.

### Step 2: what the adapters declare (read from their published packages, not run)

Read on 2026-11-05 from `@agentclientprotocol/claude-agent-acp` 0.101.0 and `@agentclientprotocol/codex-acp` 2.5.0 (both Apache-2.0), fetched with `npm pack` into a scratch folder and read, not run: neither can be driven without a login or key, and there is none here for Claude. So these are claims from source, to be confirmed by a run on a machine that has the agents signed in.

- **Embedded context: both declare it** (`promptCapabilities.embeddedContext: true`, plus images). A chip can go as an embedded resource, with the quoted text kept as the fallback for agents that do not.
- **Steering: both support it, through an extension.** Each advertises `_meta.steering.supported` on initialize and answers a `_session/steering` request that injects a message into the running turn (Claude also has `promptQueueing`). So the earlier claim here that ACP offers "cancel only" is wrong for these two adapters. isorite does not send it today, and the extension is not part of the base protocol, so other agents may not have it.
- **Subagents: both can report each as its own child session**, but only to a client that declares `clientCapabilities.subagents`. isorite's wrapper declares no such capability now (`acp-wrap.ts`). This is the likeliest way to tell a swarm apart on the Atlas, and it changes what step 4 should test.
- **Settings and slash commands:** the Claude adapter loads the user's, the project's and the local settings (`settingSources: ["user", "project", "local"]`), so a user's own CLAUDE.md, skills and MCP config apply, and it sends `available_commands_update` (the user's slash commands among them). Codex lists its own (`/status`, `/mcp`, `/skills`, `/compact`, `/review` and others). Both accept MCP servers over HTTP, which is how isorite's reaches them.
- **Resume:** both declare `loadSession` and the Claude adapter `resume`, `list` and `fork`. The Claude adapter reads Claude Code's own transcripts and uses the Claude session's id as the ACP id, which suggests a terminal session can be listed and resumed through ACP. Not run.
- **Sign-in:** the Claude adapter offers a terminal login (`claude /login`) and gateway methods, and has no login of its own. Codex advertises "ChatGPT, API key, and client-provided custom gateway authentication".
- **Terms are still open.** The Claude adapter is built on the Claude Agent SDK, and Anthropic's page says developers using the Agent SDK should use API keys, while allowing an end user to sign in to the unmodified Claude Code binary. Whether a user's subscription through this adapter, started by isorite, falls on the allowed side is not answerable from the source. It needs Anthropic's reply, or a test of what the adapter does on a subscription login. Until then isorite should not promise subscription use through ACP, and should say that it is the user's own agent and login.

What this changes: ACP is a stronger route than the plan assumed (steering, embedded context, subagent sessions), so freezing it costs more than expected. The decision to build the native harness stands, because only it can promise no shell and withdraw a chip from context, but removing ACP stays off the table.

## Steps

Each step is a commit with its tests, and the plan file is updated with what it found. A step that fails its check is reported, not worked around.

1. **Branch and baseline.** Create `m36-isorite-harness` off `m35-pi-harness`. Run the full server suite and the Playwright suite (all four projects) once, so later failures are known to be new. Done when the baseline results are in this file.
2. **Verify the ACP side and its terms.** Run the real Claude and Codex ACP adapters against an isorite session and record: whether each declares embedded-context support; which settings, MCP config and environment the Claude adapter loads; whether it advertises the user's own slash commands; whether a terminal session can be resumed through ACP or the reverse. Read how the Claude adapter is distributed and signed in, and check Anthropic's and OpenAI's pages (the OpenAI page refused a fetch in M35; use its developer docs or a browser) against it. Done when the answers are in this file and the freeze of ACP is confirmed or reversed with reasons.
3. **The paste handoff.** From the tray, produce a block of text that names the chosen notes, folders and passages and tells an agent to read them through the isorite MCP tools, with a copy button. Works with any agent that has the MCP server attached. Done when a test pastes the block into a scripted MCP client's prompt and the client's reads match the chosen items, and the text is still correct for a passage that was edited since.
3b. **ACP: chips as embedded resources.** Send each passage chip to an ACP agent as an embedded resource when the agent declared `embeddedContext`, with today's quoted text as the fallback when it did not; notes and folders stay as text that points to the tools. Done when a scripted ACP agent that declares the capability receives a resource block for the passage at the base's address, one that does not receives the quote, and the pane looks the same either way.
4. **Telling agents apart.** Two routes. Over MCP: connect several clients to the endpoint (the MCP SDK client with different `clientInfo`, and real Claude Code and one other harness if available, with subagents) and record what identity reaches `agentLook`. Over ACP: declare `clientCapabilities.subagents` in the wrapper, and record what the Claude and Codex adapters send as child sessions (step 2 found they do for a client that declares it). Done when the file states, per client and per route, whether subagents are distinguishable. If they are, a later step shows one route set per agent; if not, the display says "an agent" and this step ends there.
5. **Keep the model's context.** A session store for the native agent: write the messages after each turn, load them on resume, and rebuild the pane's turns from them where the record is missing. Done when a restart of the server resumes a pi session and a test shows the model still has the earlier turns; a corrupted store is reported, not silently dropped.
6. **Queue and steer.** Add a message queue to `PaneSessions` and `TerminalView`: a prompt sent while busy joins as a follow-up by default, and a steer is sent explicitly, with an item that shows it was queued and when it landed. Done when scripted tests send a steer during a tool run and a follow-up after it, and the pane shows both in order.
6b. **ACP: steering.** Where the agent advertises `_meta.steering.supported`, a steer sent during a turn goes through `_session/steering` and shows in the same queue item as the native agent's; where it does not, the pane offers cancel and re-send only, and says why. Done when a scripted agent that supports it receives the steer mid-turn and one that does not is never sent the request.
7. **Thinking and compaction.** Add a thinking item (collapsed by default) and a compaction marker. The host checks `shouldCompact` between turns and calls `compact` through the chosen model, then marks where the context was shortened and shows the size meter. Done when a scripted long session compacts and a test shows what the marker says; one real-model run, with its cost, confirms the summary reads sensibly.
8. **Models and keys.** A settings section to choose provider and model, enter a key or sign in with OpenRouter, and see which are configured. Keys go to a credential store in isorite's data folder (owner-only permissions), never into the base or the repository, and never into a log. Done when a key entered in the settings is used by the next turn, removed on request, and absent from the base, the repository and the test logs.
9. **Tool tiers.** Settings for the three tiers with a line under each saying what it promises and what it does not. Project read on by default; write and shell off. Done when tests show a default session cannot change a file by any tool it holds, and the settings for write and shell say in words that a shell is not confined and name the ways to confine it.
10. **Context from the tray.** Tag each given block with the chip it came from. Removing a chip withdraws its block from later requests (the earlier turns stay as history, marked withdrawn). Dragging a note or a passage into the box adds a chip. Done when a test removes a chip and shows the next request no longer carries the block, and the pane shows the difference.
11. **Several sessions.** The native agent keeps a list of sessions, opens one, forks, forgets, and resumes after a restart. Done when the pane switches between two sessions with their own turns and cost.
12. **Use it for a week.** Before any terminal interface, the owner uses the native pane for real work for a week or so, with a short list of what failed or annoyed. Done when the list is written in this file and sorted into fix now, later, and never.
13. **A terminal interface, a spike.** Decision gate after step 12: choose a library (pi's own terminal library or OpenTUI) by building the smallest client that shows the `TerminalView` and sends a prompt with a note mention, against the same routes. Done when the spike and a recommendation are written. This step happens only if step 12 says the native pane is worth continuing.
14. **The result.** What worked, what did not, what it cost to keep, and a recommendation for the next milestone: whether ACP is removed, whether the terminal interface is built, whether the swarm display is built.

## Acceptance

- A highlight in a note goes into the isorite agent's prompt as a chip, the agent answers from it, and the person sees which notes it read and changed in the pane and on the Atlas.
- A person using their own harness can paste one block and have it read the notes they chose, and what it reads shows in isorite.
- The native agent resumes after a restart with its earlier turns, can be steered or followed up while it works, shows its thinking and its compaction, and lets the person remove a chip from its context.
- By default the isorite agent cannot change a project file or run a command, and the settings say exactly what turning each on allows.
- No credential is in the base, the repository or a log.

## To verify

- What identity real MCP clients send for subagents (step 4).
- Whether OpenAI's "Sign in with ChatGPT" is open to an app that is not a listed partner, and on what terms.
- Where the session store should live so that it follows the base to a second machine or does not, and what the person expects of either. The default is isorite's data folder per base, not carried.
- Whether pi's session tree is worth using for forks (step 11) or isorite's own store is simpler.
- Whether `pi-agent-core` and `pi-ai` alone are enough for the read-only project tools, or `pi-coding-agent` is needed for them (weight: about 7 MB against about 64 MB).

## Risks

- Owning an agent is a long-term cost that version 0.13 chose to remove. Steps 5 to 11 are most of it. The one-week use in step 12 is the check that the cost is paid for.
- Claude models need API keys. People who want their subscription to pay will use the MCP route with their own harness, or the frozen ACP route. The first run needs a key before the pane works; OpenRouter's sign-in is the easiest start.
- Two agents writing one note can collide. The history keeps who changed what and can restore it, but a tester should be told, and step 12 should look for it.
- Pi still changes. Exact versions stay pinned; pi types stay inside `src/pi/`.
- A shell cannot be confined by this process. Anything that says "read-only" while the shell is on is wrong.
- Credential storage is a new place for a secret to leak. Step 8's check covers the repository, the base and the logs.

## Not in this milestone

A swarm display on the Atlas beyond step 4's test. A new Atlas layout. Marking reads on the map beyond what exists. An extension for omp or pi. A Claude subscription login of any kind.
