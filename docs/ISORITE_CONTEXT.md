# Isorite: what a fresh session needs to know

Companion to `ISORITE_DOC.md`. That document says what Isorite is to be. This one holds what was learned building its predecessor, **rdstudio**, so that a new session does not re-derive it or repeat its mistakes.

Written 2026-10-12 by the agent that built rdstudio with the developer (Lachlan), from the code and the 230 notes of rdstudio's own knowledge base. Every claim here is labelled by where it comes from:

- **Decided:** the developer said so; quoted where the words matter.
- **Built:** it exists in rdstudio and was tested.
- **Measured:** a number that was actually obtained.
- **Proposed:** the agent's suggestion, not agreed.
- **Open:** nobody has decided.

Where this document and `ISORITE_DOC.md` disagree, `ISORITE_DOC.md` is the developer's and wins; section 2 lists the disagreements so they can be settled on purpose.

## 3. Decisions that stand

The developer's, in their words where short. A fresh session should treat these as settled unless the developer reopens them.

**The name and the agent**
- The application is isorite, from *isomorphism* and *dendrite* (2026-10-09). Checked then: free on npm, PyPI, crates.io and as a GitHub user. `isorite.com` belongs to an unrelated marketplace in Florida. No trademark search was made.
- The agent is **Iso**, in both modes, one agent: "Axis becomes iso" then "Iso capitalised as it is a name. The diamond should appear in appropriate contexts" (2026-10-11).

**The style** (2026-10-11; section 4 is the specification)
- One theme, dark and light. "It's much cleaner and more minimal - which should be a trend going forward."
- "Rose sounds good": one hue for failure and destruction, nothing else.
- "The general terminal feel should be kept. No scan lines though."
- Type: "I would go Ioskeley and Departure mono"; prose stays in Charter.
- The default mode follows the system.
- Links that run against the reading order are drawn solid like the rest: "Maybe ditch the dashed lines."

**The Atlas**
- A grid of blocks and rectangular folders replaces every continuous layout (2026-10-05). Free-form folder shapes "are not ruled out later".
- Project mode is "for managing OKF and Agent workflows", not for drawing code (2026-10-07, tentative).

**Iso in the note** (2026-10-11)
- Inline, not in a sidebar. The side panels go "completely ... I want to find a different way of interacting with the agent", on the Atlas too.
- "Unkept text can be deleted so it is not written in, or verified, but until the decision is made, keep it." So Iso's text is in the file from the moment it arrives.
- The word for accepting Iso's text is "keep", not "verify".
- The purpose of the history: "This format will force the developer to be more thoughtful about their modifications to the knowledge base, doing things in more purposeful and logical chunks."
- The timeline's points "do not need to be spaced in proportion to timestamp, they just need to be in order".

**Models and search**
- Three tiers, low, mid and max, chosen by the person per request. The tool does not judge difficulty. (After a trivial edit went to the strongest model.)
- Search by meaning is local and bundled: "I want to make as much local and bundled as possible to limit the amount of setup required of the user." Notes only; code embeddings left for later.
- Questions asked on the Atlas are kept and can be replayed.

**Scope**
- "This tool is aiming at multiple targets. One is the developer workflow and enhancing/supporting developer understanding in agentic workflows, the other is education and learning, and they overlap." Breadth is intended (2026-10-08, declining a suggestion to narrow it).

**Format**
- The OKF specification is ground truth; conventions only choose among what it allows. (OKF 0.2, `github.com/GoogleCloudPlatform/open-knowledge-format`; a copy is at `~/rdstudio/reference/OKF_SPEC.md`.)
- Reports became **artifacts**: HTML files in the knowledge folders, cited from notes, never citing back.
- Only a person verifies. No agent tool can.

**How the developer works** (applies to any new repository)
- A task is planned in writing, approved by the developer, then built, then written up. Agents do not start building on their own plan.
- Git: a branch per milestone, a commit per task with a descriptive body, `--no-ff` merge to main, delete the merged branch, **never push, no remotes** unless told.
- Preferred web stack: SvelteKit and TypeScript; a typed backend producing OpenAPI, HeyAPI for the client, TanStack Query where data is truly remote.
- The developer is a thesis researcher. The first real use will be on their own research code and on a physics subject.

## 4. The style, as specified

This is the content of `knowledge/design/isorite-style.md` in rdstudio, which was written from the brand canvas (40 boards, `https://claude.ai/artifact/HQbUwuiQYL8a7Xtm1ePCbW`) and the developer's answers. Its shell and parts were then built and checked in a browser, so the rules below are known to work. A sheet with every colour pair drawn is `knowledge/design/isorite-style.html`.

`ISORITE_DOC.md` names more minerals than this palette holds (malachite and azurite among them). The built palette is deliberately three roles and one exception. A green was removed on purpose: "right" is said by the double rule. If malachite returns, decide what it means first.

### Principles

- **Three roles of colour and one exception.** Quartz neutrals for ground and text. Lattice blue for structure and for the person. Growth gold for Iso and for change. Rose for what failed.
- **One gold thing at a time.** Gold is what Iso is doing now, or the one thing of Iso's waiting on the person. Older marks fall back to text tones. Easy on a mockup, hard on a real page: check it on every screen.
- **Lines carry state,** so every state reads with colour removed.
- **Eight directions.** Nothing is rounded. No shadows, no blur, no gradients.
- **A terminal's feel:** monospace interface, numbered spaces, keys in brackets (`[1] map  [2] notes  [/] ask`), a `›` prompt, a block cursor, a status line.
- **Prose is the exception:** notes are read in a serif.

### Colour

| Token | Dark | Light | For |
|---|---|---|---|
| `--ground-0` | `#07101C` | `#F2F0EA` | the page |
| `--ground-1` | `#0C1828` | `#F8F7F3` | a frame's inside |
| `--ground-2` | `#122238` | `#FFFFFF` | a field, a raised part |
| `--ground-3` | `#1A3150` | `#E6E4DC` | a filled part, a secondary button |
| `--line` | `#23395A` | `#D3D0C5` | a rule that only divides |
| `--line-strong` | `#5C7BA6` | `#7F7D70` | a frame's edge, a dotted rule |
| `--text` | `#E9EEF5` | `#0E1726` | what is read |
| `--text-soft` | `#B4C0D2` | `#3B475B` | what supports it |
| `--text-faint` | `#8796AD` | `#5B677A` | labels and hints |
| `--lattice` | `#6BA6FF` | `#1E4FB8` | links, focus, the primary button, the person's marks |
| `--lattice-deep` | `#2D6BE0` | `#2A62D8` | a wide blue line; never under text |
| `--growth` | `#F0BE4A` | `#8C6200` | Iso |
| `--growth-deep` | `#C28F1E` | `#D9A21B` | a gold fill |
| `--rose` | `#FF8FA6` | `#A81E48` | failed, wrong, about to be destroyed |

Each of lattice, growth and rose has a soft form for a tinted ground: the colour at 16% over the ground in dark, 10% in light.

**Rose** is only for: an error, a conflict, a wrong answer, a delete or other thing that cannot be undone, a broken link. Never decoration, never a warning short of failure. **Gold** is only for: Iso's diamond, the seed being worked on, Iso's unkept text, the path Iso is taking on the map. Never a warning.

### Contrast (Measured, WCAG)

All text pairs pass AA except these, which are rules:

- No `--text-faint` on `--ground-3` (4.4 in dark). Use `--text-soft` there.
- No gold text on `--ground-3` in light (4.3).
- No text on `--lattice-deep` (3.9 dark, 3.3 light).
- `--line` is not an edge that must be seen (1.6 and 1.4). Anything a person has to find gets `--line-strong` or a fill.

### Meaning without hue

| Meaning | Shown as |
|---|---|
| Not yet: proposed, unkept, unchecked, in progress | dotted |
| Looked for, not opened | dashed |
| Opened, or linked | solid |
| Written, made permanent; reviewed, understood; right | double rule, in lattice |
| Needs work; changed since it was reviewed | a notch cut from the top right corner |
| Failed, wrong, destructive | rose, with ✕ where it stands alone |
| Partly right | a half-filled mark ◐ |
| Removed text in a comparison | struck through, faint, no ground |
| Work going on | the dotted line marches; it stops when done, and under `prefers-reduced-motion` |

As a drawn line (the map, a diagram): dotted is a 2 px stroke with dashes `2 3`; dashed `10 5`; double is two 1.5 px strokes 6 px apart.

### Type

| Face | For | Sizes |
|---|---|---|
| Ioskeley Mono | the interface, code, the map's labels | 12 px labels, 13 px default, 15 px a title; weights 400, 500, 600 on a filled button |
| Departure Mono | the wordmark, large numerals, a page's name | 11, 22 or 33 px **only**: it is drawn on an 11 px grid and blurs at any other size |
| Charter | prose, with Math Charter so KaTeX matches it | 18 px on 1.55; headings 34, 23, 19 px |

- The floor is 12 px in the interface, 11 px only on a note's block on the map.
- Labels are lower case. Capitals are not used for emphasis.
- All three are already in `~/rdstudio/app/static/vendor/fonts/` as woff2, with licences in `vendor/licenses`.
- **Ioskeley Mono is wide.** Mockups drawn in another mono do not fit. Check every screen at 390 px when it is built.
- **Maths:** KaTeX is matched to Charter by a cut of the font. Changing the serif means redoing that.

### Parts

- **A frame:** a rectangle with all four corners cut at 45 degrees by 10 px, a 1 px `--line-strong` edge, `--ground-1` inside. Its title sits in its top edge, 22 px from the left, 12 px faint text on the page's ground.
- **A button:** cut by 6 px at two corners, top left and bottom right. Primary is a lattice fill with ground-coloured text. Secondary is `--ground-3`. A quiet action is a bracketed word, `[ review ]`. Destructive is a rose fill. Pressed, where one of several, is reverse video.
- **A chip:** cut by 4 px at the same two corners.
- **A field:** not cut. `--ground-2` with a 1 px rule under it; the block cursor in lattice.
- **Focus:** a 2 px solid lattice line 2 px outside the part, square.
- **A tree** (the Library) is drawn with a tick from each folder's line to each thing in it.

**How the cut corner is made** (Built; this took three attempts). Not `clip-path`: clipping also cuts focus rings, menus that open out of a part, and scrolled content. Not two-colour quadrant gradients: they leave seams at 1× pixel density. What works is layering whole-pixel pieces of `background`: for a filled part, a centre strip, two side strips shortened by the cut, and two 45-degree gradient squares at the cut corners; for a frame, the same twice, the inside set one pixel in, with its diagonal shortened by 0.586 px so the slanted edge stays one pixel wide. The working CSS is the last section of `~/rdstudio/app/src/app.css` on `feat/m22-isorite-style`, under "isorite's parts"; copy it. Every part in every state is drawn at `#/parts` there.

### Marks

- **◆ Iso.** A filled gold diamond before the name where the name is a label on its own (a button, a tab, a heading), not inside a sentence. An empty diamond is something Iso found and did not use.
- **The person** is `you ›` in faint text. On a timeline, proposed: a blue square. Open.
- **The wordmark** is `isorite` in Departure Mono. The logo idea (the developer's): a stylised "i" with an L-system body and a geometric dot. Not drawn.

### L-systems (Built: one component; Proposed: the rules for use)

`~/rdstudio/app/src/lib/components/Sprout.svelte`, 45 lines. Axiom `X`; rules `X → F[+X]F[-X]+X`, `F → FF`; a turn is 45 degrees so the plant stays in the eight directions; a seed number decides which side each branch favours, so the same seed grows the same plant; branch tips get a small lattice square. Depth 4 at 120 px reads well.

Proposed rule, in the specification: plants are decoration. They may appear on the opening screen, in an empty state, and leaving a frame's corner (never a side). **Never in a note and never on the map**, where every mark means something. `ISORITE_DOC.md` wants them at "ends of routes" on the Atlas; that conflicts and needs deciding. A possible reconciliation: a sprout at a route's end only where the route leads somewhere not yet reached, so it means "this can grow".

### Animation, sound and automata (Open; constraints only)

Nothing here is built. What is known:

- **Animation that is information is already specified:** the marching dotted line for work in progress, and Iso's path drawn step by step on the map (section 6). A kept question replays at one step every 0.7 s. Start from these.
- **`prefers-reduced-motion`** must stop all of it.
- **Browsers block sound until the person has interacted with the page.** An audio context has to be started from a click or a key. Background sound cannot begin on load.
- **Sound should be a setting, with a clear default.** The agent's view: off until chosen, because the application is used in libraries and offices, and because a study tool that makes noise unasked gets muted for good.
- **Generative sound in a browser** is the Web Audio API: oscillators, filters, a convolver for reverb, granular playback from short buffers. No library is needed for the scale described. 1/f noise is cheap to generate (Voss-McCartney, or filtered white noise).
- **Cellular automata** suit the terminal well, since a cell is a character. A one-dimensional automaton makes a divider or a thinking indicator in one row.
- **In a terminal** an L-system tree needs a character set decided first: plain ASCII, box-drawing, or Braille. The brand brief asks for an ASCII-only form of everything.

## 5. The Atlas: what was learned

`ISORITE_DOC.md` now describes what the Atlas is. This section is how it got there and what the numbers are, so the layout is ported and not reinvented.

### History: four layouts were built and three thrown away

1. **Force-directed graph** (d3-force). Unreadable past a few hundred notes; different every time.
2. **Circle packing with forces.** Folders as circles.
3. **Contour folders, downhill routes and terrain.** Folders as contour lines, links routed downhill between them. A "calmer" pass was made on it before it was retired.
4. **The grid** (2026-10-05). Blocks on cells, rectangular folders, routes over cells. A simulated-annealing search for positions was sketched (about a minute per layout at 63 notes) and never ported.
5. **The layered layout** on the grid, each folder a layered diagram of its own. This is the one that stands.

The agent's reading of it: each continuous layout was replaced within days of being built, and the grid with a deterministic layered layout is the first the developer kept, the first that gives the same map every time, and the first that was measured.

### The algorithm (Built: `app/src/lib/views/grid/nested.js`, 519 lines)

Plain data in, plain data out; nothing after it knows how positions were chosen. It runs in a Web Worker and its result is cached by what the map contains.

- **Items.** A folder's notes and its subfolders, each subfolder already laid out and now one block. A link belongs to the lowest folder holding both ends, and there joins the two items that hold them. Links between the same two items are one trunk with a count.
- **Order.** An ordering of the items with as much link weight as possible running from required to requiring (the Eades, Lin and Smyth heuristic for a feedback arc set). Trunks against the order are back trunks.
- **Layers.** An item sits one layer after the last thing it requires. One that requires nothing sits just before the first item needing it. A layer too long for its folder wraps, cut evenly.
- **Within a layer.** Sweeps put each item at the mean place of its neighbours in the layer before; crossings are counted after every sweep and the best order kept; neighbours swap where that uncrosses; three starting orders are tried.
- **In line.** A node is joined to one neighbour in the row before (the middle one where possible, never across another join) and the two share a middle cell. Chains of joins become columns. This is what makes routes straight.
- **Groups.** Each connected group of a folder's items is a diagram of its own; unlinked items are one more. They stand in shelves, largest first.
- **Flow turns at each level:** up, then right, then up.
- **Routes.** Out of the late side of the item required, along a track of its own in the channel between two layers, into the early side of the item requiring it. Trunks from one item share their way. One that passes layers keeps a free lane in each. Of two runs that overlap in a channel, the one whose stem and drops cross the other least goes nearer its row.
- **Slants.** A trunk that turns by at most 8 cells, with nothing else in its channel within a cell, crosses in one 45-degree run with a straight cell at each end, and takes no track.
- **Back trunks** are laid out the other way round with a lane and track of their own, and drawn solid.
- **Implied trunks** (a longer way already joins the two) are hidden. When one is wanted, a router finds it a path: `router.js`, shortest paths over cells in eight directions with turns made expensive.

### Constants that were tuned

| | Cells |
|---|---|
| A note | 18 by 5 (room for a whole title on two or three lines) |
| Between neighbours, and between layers | 6 (8 where folders are involved) |
| Clear of anything a route passes | 2 |
| Inside a folder's wall | 8 |
| Under a folder's top edge, for its title | 2 |
| A folder's least width | 12 |
| A folder's contents aim to be this much wider than tall | 1.4 |
| Longest slant | 8 |

A third of each gap is thereby left for routes. The first grid stood notes 4 cells apart and was widened to 6 to give routes room.

### Measured (2026-10-11, rdstudio's own base: 225 notes, 10 folders, 178 trunks)

| | Before the last rework | After |
|---|---|---|
| Straight trunks | 29% | 53% |
| Bends per trunk, mean and worst | 3.5 and 20 | 1.0 and 4 |
| Crossings | 214 | 25 |
| Lines through a note | 0 | 0 |
| Rows the notes stand in | 178 | 77 |
| Layout time | 3 ms, then 1.5 s routing | 6 ms, no routing |

- **60% straight is not reachable by these means.** A note has one straight way in and one out. Of the trunks that turn, 73 of 83 have exactly two bends.
- **Joins must be limited** (one note's width for a note, three for a lane). Unlimited, the map grew by a third and crossings rose.
- **Slants at 8 cells** cost 2% of area for 25 slanted trunks. At 18 cells, 6% for 32.
- The bench is `bench/atlas_layout.mjs` with five kept fixtures in `bench/fixtures/atlas` and baselines in `bench/baselines/`. **Port the bench with the layout.** It is what stopped changes that looked better and measured worse.

### Not done

- **Stability under small edits.** The layout is worked out afresh each time, so one new note can move many. This is the Atlas's largest known weakness (rdstudio T140).
- **Ordering a folder's contents by where its links leave it** (T139), which would shorten routes between folders.
- **Folderize:** make a folder from the notes selected on the map (T138).
- **Drawn in the isorite style.** The drawing code (`gridmap.js`, 1,118 lines, imperative d3 over SVG) still draws the previous theme's rounded samples and grey folders.
- **SVG is slow on phones** at thousands of elements. A canvas or GPU renderer was planned (T39) and not built. In a rewrite, decide the renderer before writing the drawing, since the drawing is being rewritten anyway.
- **Scale targets** (Proposed, from the platform design): a subject of 50 to 300 notes smooth on a phone; a field of about 1,300 usable on a phone; about 4,000 works. Only the open folder's contents should be laid out and drawn in detail.

### Settings that existed

`detail` (how wide on screen before a folder opens), the lens, `hideImplied`, `gridFlow` (up, right, auto), marker shapes by note type, set in a `[map]` table of the project's config and overridable per browser. Most of the rest was for views now proposed for cutting.

## 6. Iso: the server side

The interface is being replaced (panels out, seeds in). What is underneath was built once, tested, and should be ported nearly as it is.

### One loop (Built: `packages/cli/src/agent.ts`, 114 lines)

The model is asked; each tool it calls is run and answered; it is asked again, until it replies or the tier's rounds are used, when it must reply. Rounds by tier: low 3, mid 6, max 8. Tools come in boxes (a `Toolbox` offers tools and runs calls), and a request is given the boxes it is allowed: looking things up always, writing only where the person has given leave. Every step is returned in the order made, which is what the interface draws.

- A model that cannot call tools gets one search made for it and the first three notes read.
- An input limit per call is a setting; tool replies are cut to fit and the rounds end early near it.

### Iso is given nothing and looks things up (Decided, Built)

An earlier version gathered context on the server and put it in the prompt. It was replaced: the model is given the note and the place, and read-only tools.

- Notes: keyword search, search by meaning, an outline, one section, a note's links and what links to it.
- Code (where indexed): find a symbol, outline a file, read a range.
- The instructions call search by meaning second, for when keyword search and links have not found what is needed.

### What an answer rests on (Built)

The model replies in a form: the answer, then the notes it rests on, each with the heading read and one sentence copied from the note.

- A note it never opened is dropped from the list.
- The sentence is checked against the note's text, ignoring Markdown marks and spacing. Found, it is shown as a quotation. Not found, it is replaced by the start of what the model actually read, labelled as such. **A fabricated quotation is never shown as one.**
- At most eight.

### Changes only by leave (Decided, Built; revised by seeds)

- A change in a form that was not allowed is dropped by the server and the person is told. It is not trusted to the prompt.
- Changes were exact text from the note and its replacement, not line numbers or offsets: "a model miscounts lines, and a wrong offset edits the wrong place silently. Text not found fails safe."
- With seeds, Transform returns whole paragraphs by number, which removes the "old text must match exactly once" failure for that case.
- What each kind is told, one line each (Proposed): "Answer the question. You are not changing the note." / "Write text to go at the marked point, in the note's own voice and format. Reply with that text only." / "You may rewrite the marked paragraphs and nothing else. Return each one you change, whole; leave out the ones you do not change."

### Providers and cost (Built: `provider.ts`, `models.ts`)

- OpenRouter, an API key, any OpenAI-compatible endpoint (which covers Ollama, vLLM, LM Studio, LiteLLM), and an organisation's own gateway.
- Tier defaults were Claude Haiku 4.5, Sonnet 5.5 and Opus 5.5 through OpenRouter.
- Every reply names the tier, the model, tokens in and out, tokens read from the cache, and the price. Usage is logged by feature. This already gives per-prompt cost; per-session and per-project are sums over the log.
- **Subscriptions cannot be used from a third-party application.** Providers do not allow it. The only route for a subscriber is the reverse: Isorite is an MCP server and the provider's own client (Claude Code, the Claude or ChatGPT apps as connectors) calls it. A connector is called from the provider's cloud, so the server must be publicly reachable.
- Provenance when a person keeps a model's text: `by: human:<id> with openrouter/<model>`.

### Search by meaning (Built, Measured)

- `bge-small-en-v1.5`, 8-bit quantised, 34 MB, MIT licence, run by `onnxruntime-web`'s WebAssembly build. No native binary. English only. The package grows by 49 MB.
- Each note is cut at its first- and second-level headings; a section over 1,800 characters is cut again at paragraphs. Each piece is embedded with the note's title and description before it.
- The cache is keyed by a fingerprint of the text, so editing one section re-embeds one section, and moving a note re-embeds nothing.
- Speed in Node on one thread: 11 ms a query, 132 ms a section, 80 s for 607 sections (25 s on four processes). In Chromium with the CPU slowed four times: 28 ms a query, about ten minutes for the base. Memory while embedding: about 360 MB.
- **Retrieval, 45 questions with known answers, by note:**

| Search | First | In first 5 | In first 10 |
|---|---|---|---|
| Keyword (BM25) | 51% | 64% | 71% |
| By meaning | 60% | 76% | 84% |
| Merged by rank | 62% | 73% | 80% |
| Either, asked separately | | 80% | 87% |

- Merging the two lists is no better than meaning alone. Offering both as separate tools is better than either. This is why they are two tools.
- For 16 of 45 questions keyword search returned five notes, none of which answered, without saying so.
- Task notes crowd the top of both lists (78 of 164 notes were tasks). A base that is mostly records of work needs them ranked down.
- Limits: the questions were written by the agent, who knew the notes, which favours search by meaning; each search is one query, and an agent rewords.

### How this differs from RAG, for the document's "Context" section

Typical RAG cuts existing documents into chunks, embeds them, and puts the nearest chunks in the prompt before the model sees anything. Here the unit is a note written to stand alone, with typed links and a record of who wrote and checked it; the agent navigates (search, outline, one section, a link followed) and writes back. Search by meaning is one more way to find a note worth reading. The model cannot easily tell what a similarity search missed; it can see that a note requires three others and read them.

## 7. Learning: the model that was built

`ISORITE_DOC.md` restructures where this lives (the study base). The rules themselves were worked out carefully and are in one place, `packages/core/src/learning.ts` (622 lines, pure functions over the record, 339 lines of tests).

### Three layers (Built)

| Layer | Holds | Where | Shared |
|---|---|---|---|
| Knowledge base | notes, links, references | the repository | yes |
| Learner record | what you opened, marked, practised and answered | outside the repository | never |
| Teacher | Iso's picture of you, its sources log, your changes to its skills | beside the record | never |

- **The project's id is its root commit,** the same in every clone, so teammates share a base and each keeps their own record with no configuration.
- **The record is a file of events, one per line, only ever added to.** Each carries a unique id and a hash of the note's body at the time. So merging between devices is a union, and a note changed since shows that what you knew was about an older version.
- **The learner folder is itself a git repository,** committed on every write. How Iso's picture of you changed over time is that file's history.

This is most of the study base already. What the new document adds is that exercises move there too, and that it sits beside the knowledge base on disk.

**Things to settle about the study base** (Open):
- `~/.config` does not exist on a phone. The mapping from knowledge base to study base needs a home that works there. The sync design proposed one private repository per person holding the study data for all their projects, found once at sign-in.
- Exercises in a private repository cannot be shared as a problem set with a class or a team. The built design had both: shared exercises in the knowledge base, private ones beside the record.
- The document says the user must be able to export with and without teaching data. Keeping the two in separate repositories gives that for free, which is a good argument for the split.

### States and evidence (Built)

- **States of a note:** undiscovered, discovered (opened), processed (worked through), understood. Plus "changed", when reached on an older version.
- **Evidence** is an exercise passed, or the person's own mark. Opening a page is not evidence. Iso claims understanding only on evidence.
- **Who marked** is recorded: the application (for a choice or a value), the person against the written solution, or a model, by name. All count; self-marks count less and are retested sooner.
- **Spaced recall:** boxes of 1, 3, 7, 16, 35 and 80 days. At most eight offered at once.
- **Load:** said once, when today is at least twice the usual day and eight notes or more, with a suggestion to stop.

### Streaks, and the conditions on them (Decided)

Shown for recall, new learning, problem solving, and all three. The conditions are the substance:

- Only work that teaches counts. Opening pages does not. An exercise given up does not; one finished with hints does.
- A day with nothing due is a rest day. An empty queue never breaks a streak.
- A day runs 4 a.m. to 4 a.m. A week counts with four days.
- One reprieve is earned per seven days, banked up to two, used automatically.
- Streaks never count as evidence of understanding.
- Worked out from the record alone, so they are the same on every device.
- Reopen if streaks are seen to push volume over understanding.

### Iso as teacher (Built)

- **Skills are plain text** served to whichever model runs them, with the person's private overrides winning over the defaults: `assess`, `map`, `source`, `exercise`, `next`, `review-changes`.
- **Rules across all of them:** understanding is claimed only on evidence; every claim taught is sourced; a mistake is said plainly, without flattery; one or two things are asked at a time.
- **Three profiles of project:** a topic (ground truth is texts, cited to the page), a codebase (ground truth is the code), a project (ground truth is decisions still being made).
- **The profile of the learner** (strong, struggling and the likely reason, how you learn, what to retest) is written only by `assess`, and **every claim cites the events behind it by id.** A claim with no evidence is not written. The person can dispute a claim by editing the file; the history keeps both.
- **A sources log:** what was searched, what was found, what was chosen or rejected and why.

This is the "hidden knowledge base purely for Iso's teaching purposes" in the document. It exists.

### The exercise bench (Built, partly restyled)

- Three columns: the exercise, your answer, Iso's marks in the margin.
- Iso offers a hint (up to three), feedback, and discussion. Each mark quotes the passage it is about and keeps the version of the answer it was made on.
- The answer is saved as typed, with versions that can be restored.
- "Ask Iso to mark it" or "Mark it yourself" against the solution, which is hidden until then.
- A board for this in the isorite style is at `#/parts/bench` on the m22 branch, with pictures in `knowledge/tasks/t122-*.jpg`. Whether the leader lines from answer to mark stay was left open.

## 8. The note format: specifics

- **Frontmatter:** `type` is the only required field; unknown keys and types must be tolerated. `title`, `description` (one sentence, and it matters: search and embeddings both use it), `tags`, `status`, `generated: {by, at}`, `verified: [...]`.
- **Actors:** `human:<id>`, `<harness>/<model>`, `process:<tool>`.
- **Link kinds** are the link's Markdown title, which is plain CommonMark and so stays valid everywhere: `[tangent space](/manifolds/tangent-space.md "requires")`.

| Kind | Meaning |
|---|---|
| `requires` | cannot be understood without it; it comes first |
| `uses` | relied on, not needed to define it. An unrated link counts as this |
| `see also` | a forward reference or a tangent; takes no part in the layout |

  `ISORITE_DOC.md` also lists "mentions". That is a fourth kind and is new; decide whether it differs from `see also`.
- **Links are bundle-absolute** (`/folder/note.md`). Broken links are tolerated and reported.
- **`requires` cycles** are warned about; they make study paths meaningless.
- **A study path is only as good as the `requires` links.** A note that uses a concept without linking to it looks like a starting point.
- **`index.md` files are generated,** never edited by hand or by an agent.
- **Diagrams are Mermaid** in a fenced block, so they are text that people and agents can both edit and diffs show.
- **Pictures** (M22, built): Markdown images, drawn in place in the note, pasted or dropped and named before they're saved (in a folder named for the note), chosen with `[[!`, and on the Atlas with the Pictures switch. `code:` shows one from the repository. Iso reads a picture's alt text, not the picture.
- **Artifacts:** one self-contained HTML file beside the notes, under 200 kB, with its title, description, date and author in `<meta>` tags. A note cites one as a link or shows it in place with image syntax. Since M23 it is drawn: in a sandboxed frame given its document through srcdoc, with isorite's kit (`packages/kit`: two themes of the same custom properties, markup-first elements, charts on Plot, 3D on three.js, maths on KaTeX, everything shipped with isorite and nothing fetched) and the data its `isorite:uses` names. Iso builds one with `artifact_recipe`, `read_data` and `write_artifact`, which checks the kit's rules and runs it unseen. A file whose name starts with `_` is a draft.
- **Unkept text** (Proposed): fenced by comment lines, `<!-- seed:k3f9 unkept -->` and `<!-- /seed:k3f9 -->`. Markdown renderers do not show them, so the file reads correctly anywhere. Keeping removes the closing fence and the word `unkept`. Open: whether the developer accepts comments in the file, and whether git may commit a note that has them.
- **A paragraph,** for handles and Transform: text with a blank line above and below. A list, a fenced block, a table, a displayed equation and a heading each count as one.

## 9. Terminal agents and the browser

`ISORITE_DOC.md`'s TUI section rests on this, and the data side of it is built.

### Built

- **The MCP server** gives a terminal agent the base: `brief`, `search`, `find_similar`, `outline`, `read` (one section at a time), `list_concepts`, `backlinks`, `record` (create or change a note, stamping who and when), `review_queue`, `study_path`, the learner and exercise tools, the teacher's files and skills, and `from_developer`.
- **Retrieve progressively:** search, then an outline, then one section. This is the server's standing instruction and it is what keeps an agent's context small.
- **The agent's path, live.** Every MCP call is traced: what was searched for, which notes were found and opened, which section, what was written. Never the text itself. The browser follows the log over a standing stream and marks the map as the agent works, with the same drawing as Iso's own path. No model need be connected to watch.
- **Reads and edits made outside MCP** are caught by a harness hook that reports `{tool, path, query, session, client}`. Built for Claude Code (a `PostToolUse` hook, run in the background because the command takes half a second to start). Not built for OpenCode or Pi.
- **From the browser to the agent:** "send to agent" passes a message and the note or folder selected to whichever terminal agent asks next, once. Nothing the person does in the application reaches an agent except what they send. A session already running learns of it only when it calls the tool.
- The log is private, outside the repository, capped at 4 MB.

### Not built: the terminal surface itself

Six things were wanted (the developer, 2026-10-10): edits seen live in the browser; notes brought into context and paths found, shown; a referenced note opened in the browser by clicking it in the terminal; buttons for Isorite's own actions, including starting it; branding with ASCII L-system trees and a splash; the notes in play listed in the terminal.

A time-boxed experiment was scoped to find out, for Pi and for OpenCode, which of the six each can deliver, with screenshots, before choosing between a plugin, a launcher on top of Pi, and a custom TUI. **It was never run.** It is `knowledge/tasks/T116-terminal-surface-spike.md` in rdstudio, and it should be the first thing done on the TUI. Its open questions include which terminal emulator the developer uses (clickable links and mouse reporting differ) and whether a harness's own branding may legally be replaced.

## 11. Engineering lessons

Small things that each cost an hour or more.

- **Browser tests select by text and role,** not by class. The isorite restyle of the shell and every shared part needed changes in only five of the twelve suites for that reason. Keep doing it.
- **Two suites were flaky** and stayed so (a proposal test about one run in four, a sign-in test about one in two). The first fails waiting for cards that arrive from a stream; the cause of the second was never found. In a rewrite, give streamed parts a state a test can wait on.
- **Verify in a browser, in both modes, at 1280 and 390 px, before calling a screen done.** Several defects of the restyle showed only at 390 px or only at 1280 px.
- **A fixed status line at the bottom covers a phone's tab bar** unless it is hidden there.
- **A long project name pushes the bar's other parts off the screen** at 1280 px in a wide mono. Decide which part gives way.
- **Exact-text edits from a model fail safe; offsets and line numbers fail silently.**
- **Never show a model's quotation without checking it against the source.**
- **A trace or a log must never be able to fail the call it is recording.**
- **A layout cache needs a version number,** bumped whenever the layout changes, or browsers keep the old map.
- **Two implementations of one thing drift.** The Python core fell behind the TypeScript one within days and was deleted, 5,600 lines. Do not start a second implementation of anything, a TUI's copy of the map included.
- **Theming by aliasing old token names to new values** restyles everything in a day and leaves the old names in the code for good. In a new codebase, use the final names from the first line.
- **Departure Mono at any size but 11, 22 or 33 px is blurred.**
- **`clip-path` for cut corners breaks focus rings and menus** (section 4).
- **Imperative drawing code beside a component framework** (the map and its panel were plain JavaScript driven from one Svelte wrapper) made every later change to the map's interface slow. If the map is redrawn, make its chrome components and only its canvas imperative.
- **A model's cost should be on the screen every time.** Seeing what one trivial edit cost on the strongest model is what led to tiers.

## 12. Starting fresh: the agent's recommendation

Asked on 2026-10-12 whether to start the project again from the ground up. The answer given: **yes to a new repository, no to writing everything again.**

### Why a new repository is reasonable

- The code is 19 days old and was cheap to produce. What was expensive was finding out what to build, and that is in the knowledge base and this document, not in the code.
- The remaining plan for rdstudio (finish the restyle, replace both agent panels with seeds, add the journal, rename every package, command and config file, drop the Python wheel) already replaces most of the interface. Doing it in place means carrying three generations of names (`teacher`, `axis`, `iso`; `rdstudio`, `isorite`) and four generations of style through every step.
- Nobody depends on rdstudio. There are no users to migrate and no data to convert except its own knowledge base.
- The new document changes load-bearing structure: the study base, the modes, seeds in the file format.

### Why not from nothing

Three parts hold most of what was hard-won and are nearly independent of the interface. Copy them, with their tests, on the first day:

| Part | Files in `~/rdstudio` | Why |
|---|---|---|
| The core | `packages/core/` | OKF parsing, lint, the graph, search, the learning rules; 592 lines of tests; conformance fixtures in `fixtures/` |
| The Atlas layout | `app/src/lib/views/grid/` (`nested.js`, `router.js`, `cells.js`, `grid.test.js`), `bench/atlas_layout.mjs`, `bench/fixtures/atlas`, `bench/baselines` | Five layouts were tried to get here |
| Iso's server side | `packages/cli/src/agent.ts`, `lookup.ts`, `provider.ts`, `models.ts`, `embed.ts`, `trace.ts`, and the reading of a reply in `atlasask.ts` | Section 6 |

Also worth lifting: the MCP server (`mcp.ts`, `store.ts`, `brief.ts`), the editor's live preview and link control (`app/src/lib/editor/`), the cut-corner CSS and the token file (`app/static/themes/isorite.css`, minus its alias block), the fonts, `Sprout.svelte`, and the retrieval measure (`bench/retrieval/`).

Rewrite: every page, the map's drawing, the server's routes, the configuration, the command line's surface.

### The risk a rewrite does not remove

In 19 days the project had four visual styles, five map layouts, two agent names and two interfaces to the agent, and was never once used to study a subject or run a project. The new document adds sound, automata, a TUI, a desktop and mobile application, team use and research-driven base building, under a heading that says the feature set is kept minimal. A new repository makes all of that easier to start and no likelier to finish. The danger is a second system that is larger than the first and equally untested.

So the recommendation carries conditions:

1. **Write the cut list before the first commit.** Section 2's second table, each line answered.
2. **Settle the format questions first** (section 13, the first group). Seeds, the journal and the study base all write to disk; changing them later means converting data.
3. **Build one thin slice end to end, then use it.** A base, the editor with seeds, the Atlas, one exercise, on a desktop browser. Then learn a real subject with it for a week before adding anything. The trial that was planned and never run (dynamical mean-field theory) is the obvious one.
4. **Sound, automata, the TUI, Tauri and mobile wait** until the slice has been used. Each is independent of the others and none changes the format.
5. **Keep rdstudio as it is** on `main`, as the working reference, and merge or abandon the m22 branch on purpose rather than by neglect.

### A possible order (Proposed)

1. Repository, names, the core and its tests carried over. The command and the config file named for isorite from the start.
2. The style: tokens, type, the parts page. One day, since it exists.
3. Reading and editing a note. Live preview and link controls carried over.
4. Seeds: Answer, then Insert, then Transform, with the file fences and "keep".
5. The Atlas: layout carried over, drawing rewritten in the style, on a renderer chosen for phones.
6. Iso's path on the Atlas; seeds on the Atlas.
7. The journal, the timeline, the session tour.
8. The study base: the record carried over, exercises in their new form, the bench.
9. **Use it.** Then decide what is next from what was missed.

### Bootstrapping the new repository's own knowledge

Isorite should keep its own design and decisions in an Isorite base, as rdstudio did. Until Isorite can host itself, the published `rdstudio` 0.4.0 can serve a `knowledge/` folder in the new repository (the format is the same), and its MCP server gives a terminal agent `brief`, `search` and `record` there. `ISORITE_DOC.md` and this file are the first two things to put in it, split into notes.
